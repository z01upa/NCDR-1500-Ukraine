# NCDR 1500 - географічний Reader для CD_7190

Стан: 27.10.2026. Цей пакет створено з **Ваших** розпакованих EUZ logical.bin з CD_7190, версія даних `EU44420940.82`. Працює офлайн на Windows 11 з Python 3.10+; сторонні бібліотеки не потрібні.

## Підтверджені результати

| Файл | Кількість записів | Розмір одного запису | Встановлено |
| --- | ---: | ---: | --- |
| EUZ.CNY | 1 109 | 174 | назви регіонів, індекси 0..1108 |
| EUZ.CTY | 26 525 | 178 | назва міста, його ID, посилання на регіон, координатні межі |
| EUZ.CL | 26 949 | 44 | посилання на ID міста й варіант назви |
| EUZ.RL | 249 750 | 61 | назва дорожнього запису, числове поле, поки лише кандидат на індекс IOF |
| EUZ.IOF | 150 293 | 6 | підтверджено фіксований розмір; семантика не доведена |
| EUZ.TYP | 1 252 | 54 | назви типів вулиць/доріг |
| EUZ.CT | 47 251 | 14 | підтверджено фіксований розмір; семантика не доведена |

У цих файлах фіксована область заголовка становить 94 байти. Значення типу зберігається за офсетом 84 (u16 LE), лічильник записів - за офсетом 86 (u32 LE). Для **цих семи файлів** перевірено `actual_file_size == 94 + count * stride` (для інших EUZ.* загальний формат може відрізнятися).

### EUZ.CTY: структура запису 178 байтів

| Зміщення від початку запису | Розмір | Зміст |
|---|---:|---|
| +0 | 4 | City ID: u32 LE, у всіх 26 525 записах дорівнює номеру запису |
| +4 | 4 | Region ID: u32 LE, посилання на EUZ.CNY |
| +8 | 10 | нульові байти на перевіреному наборі; призначення невідоме |
| +18 | 4 | західна межа: int32 LE / 100000 |
| +22 | 4 | південна межа: int32 LE / 100000 |
| +26 | 4 | східна межа: int32 LE / 100000 |
| +30 | 4 | північна межа: int32 LE / 100000 |
| +34 | 144 | назва (нуль-термінована, однобайтне кодування CP1252 на цьому наборі) |

Для 26 525/26 525 записів перевірено послідовність ID, правильний порядок географічних меж, припустимі координати, дійсний зв'язок з CNY. Використовуються всі 1 109 регіонів CNY. Координати - **bounding box**, не центральна GPS-точка міста й не геометрія дорожньої мережі.

### EUZ.CNY: регіони

174 байти на запис, ID регіону u16 LE за +0, назва за +30. Всі ID 0..1108 ідуть послідовно. Додаткові байти залишаються недослідженими.

### EUZ.CL: варіанти назв

44 байти на запис, u32 City ID за +0, назва з двох частин за +4..+5 та +6..+43. Усього 26 949 записів: 24 286 збігаються з назвою міста з CTY, інші 2 663 відрізняються (альтернативна мова, форма, розширений підпис тощо). 25 929 різних City ID мають хоча б один запис CL. Деякі альтернативи: `ÅRHUS -> AARHUS`, `AACHEN -> AIX-LA-CHAPELLE`, `SWANSEA -> ABERTAWE`. Точну логіку формування всіх альтернатив ще потрібно вивчити.

### EUZ.RL / IOF: структурна гіпотеза

Для 249 750 RL записів 4-байтове число за +0 завжди лежить у межах `0..150292`. Це рівно діапазон індексів 150 293 фіксованих IOF-записів. RL назва розміщена за +7; IOF має по 6 байтів на запис. **Можливий зв'язок RL -> IOF, проте призначення цього числа поки не доведене.** Тому в CSV воно називається `ref_candidate_iof_index`.

## Файли пакета

- `decode_geography.py` - Reader із перевіркою структур, обмежень та контрольних сум за початковим EVIDENCE.json, якщо він доступний.
- `START_WINDOWS.cmd` - запуск на Windows. Якщо дані не лежать поруч, відкриється діалог вибору `EUZ.CTY.logical.bin` у папці, де також мають бути інші файли.
- `test_geography.py` - п'ять самодостатніх модульних тестів.
- `OUTPUT_GEO/EVIDENCE_GEOGRAPHY.json` - докази на наданих Вами оригінальних розпакованих даних.
- `OUTPUT_GEO/cities.csv`, `regions.csv`, `city_lookup_aliases.csv`, `road_names.csv`, `street_types.csv` - машинозчитувані декодовані записи (UTF-8 with BOM для Excel).
- `OUTPUT_GEO/city_bbox_centers.geojson` - умовні центральні точки bounding box для перегляду в GIS (це **не** справжні центри міст).

## Запуск на Lenovo

Розпакуйте ZIP в окрему папку та двічі відкрийте `START_WINDOWS.cmd`. Якщо з'явиться вікно вибору файла, вкажіть `EUZ.CTY.logical.bin` зі старої теки `LAB_OUTPUT/decoded` (інші EUZ.* повинні лежати там само). Новий результат створиться у `OUTPUT_GEO` поруч із командним файлом. Якщо така папка вже існує, створюється нова з часовим суфіксом; старий результат не перезаписується.

Тут усе вже було прогнано на наданих Вами EUZ.*; повторний запуск потрібен лише якщо необхідна копія таблиць на самому Lenovo.

## Що далі для реального диска

1. Перевірити ці сім схем на `IZ.*` та `SCZ.*` з інших оригінальних комплектів (не припускати однаковості формату).
2. Встановити семантику IOF і довести або спростувати посилання RL -> IOF.
3. Дослідити місько-дорожній зв'язок у `EUZ.CT`, а також `RT`, `MP0`, `MG1/2/3` і програму, яка їх читає.
4. Лише після доведеного декодера геометрії й індексів створювати експериментальний Writer на **синтетичному наборі** та перевіряти round-trip.
5. Далі створити малий кандидат диска для NCDR 1500 і провести випробування в автомобілі, після чого конвертувати карту України.

Застереження: цей архів **не є образом CD для NCDR 1500**. Він не містить доведеного маршрутизатора, нового writer для дорожньої геометрії чи перевірки кирилиці.

## Додатковий аналіз `MP0/MG1/MG2/MG3` із оригінального архіву

У перших 110 байтах кожного файлу після заголовка на зміщенні +94 зберігаються чотири знакові `int32 LE`, що за масштабу `1/100000` узгоджуються з географічними межами карти. Для `MP0` це `[-9.16181, 36.26352, 30.20566, 73.17051]`; **ці межі включають усі 26 525 bounding boxes з CTY**. Для `MG1`, `MG2`, `MG3` межі дещо інші й не включають усі міста, що узгоджується з різними рівнями/покриттям, але не доводить призначення кожного файлу. Деталі - `OUTPUT_GEO/SPATIAL_HEADER_EVIDENCE.json`. Ніякого декодування геометрії всередині MG/MP0 тут ще не виконано.
